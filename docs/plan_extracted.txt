1. FOUNDATION: WHAT THE SITE MUST COMMUNICATE
======================================================================
This plan is grounded directly in the USWAG Constitution and By-Laws: the organization's three advocacy pillars (youth voice, mental health & wellness, environmental leadership), its dual-entity governance (officers vs. general membership), its annual officer/membership cycle, and its reporting obligations to the SARS Office and the university adviser. The website should function as the organization's digital headquarters — not just a brochure, but the operational hub for events, membership, and institutional memory.
Core Advocacy Pillars (Article II)
Youth Voice & Participation — student involvement in governance and civic leadership
Mental Health & Wellness — literacy, peer support, wellness campaigns
Environmental Leadership — sustainability efforts and green initiatives
Two Governance Entities to Reflect in the System
Admin (Officers) — manage content, events, membership, officer transitions, and bylaws
Member (Org Family) — verified card-carrying members who built the org's history and legacy

======================================================================

--------------------------------------------------
2.1 Color Palette
--------------------------------------------------
A single palette applied consistently across every page, component, and the PWA icon/splash screen.

Deep Forest
#142718 | Primary Green

#E7EFE4


Token | Hex | Primary Use
Deep Forest (#142718) | #142718 | Headers, footer, nav bar, body text on light bg, dark-mode surface
Primary Green (#2E5B41) | #2E5B41 | Buttons, links, active states, section headings
Sage Accent (#98CBB0) | #98CBB0 | Hover states, badges, chart accents, QR frame, progress bars
Mist Background (#E7EFE4) | #E7EFE4 | Page background, cards, input fields

Accessibility check
Deep Forest on Mist Background → passes WCAG AA for body text
White text on Primary Green → passes AA for buttons/nav
Sage Accent is used for accents/hover only, never as body text on white — contrast is too low

--------------------------------------------------
2.2 Typography & Visual Hierarchy
--------------------------------------------------
Headings: a confident, slightly rounded sans-serif (e.g. Poppins / Sora) for a modern, youth-forward feel
Body: a highly readable sans-serif (e.g. Inter / Manrope) for long-form content like bylaws and reports
Scale: establish 5–6 fixed steps (e.g. 12/14/16/20/28/40px) reused everywhere — no ad-hoc sizes
Hierarchy cues: weight + color + spacing before size alone; Primary Green for section labels, Deep Forest for headlines, grey for metadata
Generous white space and card-based grouping so dense content (officer duties, bylaws) doesn't feel like a wall of text

--------------------------------------------------
2.3 Modern Interaction Patterns
--------------------------------------------------
Sticky, translucent nav bar with scroll-aware shrink
Motion: subtle fade/slide-in on scroll (Framer Motion), never blocking or slow
Skeleton loaders instead of spinners for content-heavy pages (events, news feed)
Dark-mode variant using Deep Forest as the dominant surface (nice-to-have, phase 2)
Floating action button for the notification bell / install-app prompt, consistent with PWA feel

3. TECHNICAL ARCHITECTURE
======================================================================

--------------------------------------------------
3.1 Stack Overview
--------------------------------------------------

Layer | Technology | Notes
Frontend | React (Vite) + TypeScript | Vite over CRA for faster builds; TS recommended for a multi-role app
Styling | Tailwind CSS + custom design tokens | Map the palette to Tailwind theme colors directly
State/Data | React Query + Zustand | Server cache vs. lightweight UI state, kept separate
Backend | Node.js (Express or Fastify) | REST API; Fastify if you want built-in schema validation
Database | PostgreSQL (Neon/Supabase) | Relational fits members, events, attendance, officer terms well
Auth | JWT + refresh tokens, bcrypt | Separate role claims for admin sub-roles vs. member
File/Image storage | Cloudinary or Supabase Storage | Member photos, QR images, event banners
Push Notifications | Web Push API + service worker | Free, no vendor lock-in; works installed or in-browser
QR Generation | qrcode (node) + jsQR / html5-qrcode (scan) | Server-generated signed payloads; camera-based scan on officer phones
Facebook Sync | Meta Graph API + scheduled job | Cron (node-cron or Vercel Cron) pulls Page posts periodically
Hosting — Frontend | Vercel | As planned; PWA-friendly, fast edge CDN
Hosting — Backend | Railway or Render | Vercel serverless functions are workable too, but a persistent Node service is simpler for cron + websockets
CI/CD | GitHub Actions → Vercel auto-deploy | Preview deployments per pull request

Why not put everything in Vercel serverless functions?
Vercel works great for the frontend and can host light API routes, but a scheduled Facebook sync job and QR/attendance logic benefit from a small always-on Node service (Railway/Render both have generous free tiers for a student org). This keeps Vercel doing what it's best at — fast static + edge delivery — while a lightweight backend owns the database and integrations.

--------------------------------------------------
3.2 PWA Requirements
--------------------------------------------------
Web App Manifest — app name, icons (192/512px), theme_color: #142718, background_color: #E7EFE4, display: standalone
Service Worker — offline shell caching for public pages + push notification handling (Workbox recommended)
Install prompt — custom “Add USWAG to your home screen” banner for logged-in members, respecting the browser's native beforeinstallprompt event
Push notifications — opt-in permission flow; triggered server-side on new event, announcement, or officer/bylaws update
Floating in-app notification bell with unread badge, in addition to native push, so it works even when notifications are off

--------------------------------------------------
3.3 Facebook Page Auto-Sync
--------------------------------------------------
Create a Meta Developer App and request Page Public Content Access (or use a Page Access Token if USWAG admins manage the Page).
Backend cron job (e.g. every 30–60 min) calls the Graph API /{page-id}/posts endpoint.
New posts are parsed (text, image, permalink, timestamp) and upserted into a posts table, deduplicated by Facebook post ID.
The News/Updates page renders these as native-feeling cards — styled in the USWAG palette — with a “View on Facebook” link out.
Optional: flag posts matching keywords (“seminar”, “event”) to auto-suggest creating a matching Events entry for RSVP.

4. USER ROLES & PERMISSIONS
======================================================================
Per your direction: two admin tiers plus the general member role, reflecting Article VI's officer structure.

Role | Who | Can Do
Super Admin | President (+ delegated VP) | Everything below, plus: manage officer accounts/roles, edit bylaws/constitution page, approve amendments, view all analytics, issue/revoke admin access each academic year
Officer Admin | Secretary, Treasurer, Auditor, Business Manager, PROs | Scoped by role: Secretary → members/minutes/announcements; Treasurer → dues/finance reports; Auditor → view financial + attendance records; PRO → news/social content; all can create events and scan QR at assigned events

This mirrors Article VI's duties (Secretary keeps records, Treasurer manages funds, Auditor examines records, PRO disseminates content) directly into scoped permissions — so the system enforces what the Constitution already assigns on paper.

5. UNIQUE MEMBER QR SYSTEM
======================================================================

--------------------------------------------------
5.1 How It Stays Non-Duplicable
--------------------------------------------------
Each member record gets a server-generated UUID at approval — never a guessable sequential ID
The QR encodes a signed token (UUID + HMAC signature using a server secret) rather than raw data — a photocopied or screenshotted QR still scans, but any tampered/regenerated QR fails signature verification
Optional short-lived rotating layer (phase 2): QR refreshes a rotating component every N hours for high-stakes events, so an old screenshot alone can't be reused later
Every scan is logged (who scanned, when, which event) — a member “used” at two physical locations minutes apart is instantly visible to admins

--------------------------------------------------
5.2 Verification Flow (Officer's Phone)
--------------------------------------------------
Officer opens the mobile-optimized Scan page (role-gated, camera access via html5-qrcode)
Camera reads the QR → sends signed token to the backend
Backend verifies signature + checks member status (active/expired per Article III's annual renewal) — responds Valid / Invalid / Expired
Valid → green confirmation card with member name, photo, college/dept; auto-logs attendance for the selected event
Invalid/cloned → red warning card, no attendance recorded, flagged for admin review

--------------------------------------------------
5.3 What the QR Powers
--------------------------------------------------
Event attendance logging (in-campus and out-of-campus activities)
Eligibility basis for selecting participants in limited-slot activities, based on attendance history/standing
Digital membership card — viewable/downloadable from the member dashboard, shown as proof of active membership
